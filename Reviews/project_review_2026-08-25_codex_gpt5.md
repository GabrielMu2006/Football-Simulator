## 做得好的地方

### 1. 玩法闭环真实存在

`football_simulator/state.py` 不仅推进联赛，还处理杯赛、附加赛、转会、选秀、能力审核、赛季归档和荣誉。端到端验证表明这些模块能够跨三个赛季协同工作，长期玩法不是仅停留在 UI 展示层。

### 2. 基础领域约束清楚

`football_simulator/models.py` 通过不可变数据类和 `Team.__post_init__` 强制 11 人及 1/4/3/3 位置约束；交易和选秀后还会再次校验 40 队阵容完整性。这些防线有效避免了大量隐性脏数据。

### 3. 配置校验和随机建档较扎实

`football_simulator/data.py` 对球队数量、唯一性、能力区间、位置和首批真实球员容量进行验证；新存档独立复制并随机化配置，符合 README 描述的“存档专属世界”设计。

### 4. 赛程实现简单且可验证

双循环轮转算法产生的对阵数、主客场数和周历映射均符合预期。赛程、比赛引擎和状态推进在文件层面有基本职责分离。

### 5. UI v2 已按页面拆分

仪表盘、比赛、球队、球员、杯赛、转会、选秀、历史和存档各自成页，比把全部图形逻辑放在单一窗口类中更易维护。现有 `large_table_page.py` 也体现了对大表格复用的进一步抽象。

### 6. macOS 发布物当前结构完整

应用签名、plist 和 zip 均通过只读校验，外置配置与本地源码启动器也为签名/兼容性问题提供了实际退路。

## 主要问题与建议

### P1：存档路径没有形成可靠的目录边界

证据：

- `football_simulator/runtime.py:165-170` 只拒绝 `/`，没有拒绝 Windows 的 `\\`、盘符或 UNC 路径。
- `football_simulator/runtime.py:107-112` 会对拼出的路径直接调用 `shutil.rmtree`。
- `football_simulator/state.py:3679-3680` 甚至没有调用 `normalize_save_name`，直接把外部 `save_name` 拼到 `save_root()` 后。

影响：Windows 上可用反斜杠或绝对盘符让创建、读取、写入或删除操作越出 `saves`。在 macOS/Linux 上，直接调用状态 API 或 CLI 传入包含 `../` 的名字，也可能越界读写结构匹配的 `state.json`。这是本项目最高优先级的数据安全问题。

建议：只允许有限字符集的单段存档名；所有路径入口统一走一个校验函数；对 `candidate.resolve()` 做“必须位于 `save_root.resolve()` 之下”的最终包含性检查；删除前再次验证目标是直接子目录且不是符号链接。Windows 还应处理保留设备名、盘符和 UNC 路径。

### P1：状态文件写入不是原子的，异常中断可能损坏唯一存档

证据：`football_simulator/state.py:3702-3706` 直接用 `Path.write_text` 覆盖 `state.json`，没有临时文件、原子替换、备份或 `fsync`。

影响：每周模拟、能力审核、交易和选秀都会覆盖完整 JSON。进程崩溃、断电、磁盘写满或杀进程发生在写入中间时，可能只留下半截 JSON；读取端只能报“存档文件无效”，没有自动恢复路径。

建议：先在同目录写入 `state.json.tmp`，刷新并 `fsync` 后用 `os.replace` 原子替换；替换前保留一份最近成功的 `state.json.bak`。为状态增加 `schema_version`，加载时做结构校验和可控迁移。

### P1：Windows 图形版构建配置引用了仓库中不存在的文件

证据：`Football Simulator UI v2 Windows.spec:13-16` 同时打包中文配置和根目录的 `football_simulator_config.json`，但根目录实际不存在后者；`build_windows_ui_v2.bat` 直接使用该 spec，也没有预先创建英文副本。

影响：按当前脚本在 Windows 上重新构建，PyInstaller 的 data 收集阶段预期会因源文件缺失而失败。README 虽说明发布包提供英文副本，但当前只在 macOS 构建脚本中复制该文件。

建议：Windows 构建前明确复制中文配置为英文副本，或从 spec 中移除不存在的输入并在产物阶段复制；随后在 Windows CI 中执行最小打包和启动冒烟。

### P2：没有自动化测试和 CI，复杂状态机缺乏回归防线

仓库没有测试文件、测试配置或 CI 工作流，而 Python 源码约 12,714 行，`state.py` 单文件约 3,941 行。当前人工冒烟通过只能说明这次抽样路径可工作，无法覆盖随机分支、旧存档兼容、并列排名、杯赛平局、转会重算和异常写盘。

建议优先建立以下测试层：

1. 纯单元测试：赛程、积分、比赛统计、排名规则、球员 ID、路径校验。
2. 属性/不变量测试：每队 38 场、对阵两次、阵容始终 11 人、真实球员唯一、升降级后仍为 20+20 队。
3. 状态机集成测试：连续三赛季、全部批准/全部拒绝交易、选秀池耗尽、存档迁移。
4. 构建冒烟：macOS 与 Windows 至少导入 UI 入口、完成 PyInstaller Analysis，并校验产物包含配置。

### P2：依赖与入口不完全一致，构建也不是严格可复现的

- `terminal_main.py` 依赖 `rich`，但仓库只有 `requirements-ui-v2.txt`，其中没有 `rich`；从 README 的安装命令创建环境后，终端 UI 不能直接运行。
- `requirements-ui-v2.txt` 使用范围版本 `PySide6>=6.10,<6.11` 和无上界 `pyinstaller>=6.0`，与 README 所称“固定版本”不一致。
- `build_macos_ui_v2_app.sh:17-22` 仅在 `pyinstaller` 可执行文件不存在时安装依赖；已有但过期或不完整的虚拟环境不会按最新 requirements 对齐。

建议：明确支持的入口并拆分运行依赖与构建依赖；提供锁定文件或至少兼容性约束；构建脚本每次执行幂等的依赖同步，或基于锁文件创建干净构建环境。

### P2：仓库把源码和完整发布运行时混在 Git 历史中

当前 Git 跟踪 372 个文件，其中 325 个位于 `release/`；本地 `.git` 约 101 MiB，已跟踪的 macOS zip 约 32 MiB，同时还跟踪 `.app` 中大量 Qt/Python 二进制。二进制更新会产生大块不可审阅 diff，代码审查、克隆和版本历史都会持续膨胀。

建议：优先把正式二进制放到 GitHub Releases，并在仓库保留源码、构建清单和校验和；如确需版本化大文件，使用 Git LFS。不要同时跟踪解压后的 `.app` 和同内容 zip，除非有明确的离线分发需求。

### P2：核心状态模块职责过载

`state.py` 同时承担存储、迁移、赛季推进、联赛排名、杯赛、附加赛、转会、选秀、评分、市值、荣誉和查询投影；`interactive_cli.py` 约 1,554 行，`cups_page.py` 约 941 行。任何跨系统修改都容易触发远距离副作用。

建议按领域逐步拆分为 `storage`、`season_service`、`competitions`、`transfers`、`draft`、`awards` 和只读 `queries`，先用测试锁住行为，再移动代码。不要一次性重写整个状态机。

### P2：macOS 发布物只支持 Apple Silicon，但文档没有明确标注

本地发布应用经 `file` 确认为 arm64，构建脚本也强制 `arch -arm64`。Intel Mac 无法运行 arm64 应用，而 README 目前只写“macOS 图形版”。

建议在下载位置和 README 明确写“Apple Silicon”；如需 Intel 支持，分别构建 x86_64/arm64 产物或研究 universal2，并在对应硬件/CI 上验证。

### P3：配置只校验原始姓名，不校验生成后的球员 ID 冲突

`real_player_id` 会把标点和空格折叠为 slug，而 `data.py:295-315` 没有检查姓名重复或 slug 冲突。不同写法如标点差异可能得到同一个 `real::...` ID，之后的阵容标准化会把重复 ID 视为冲突并替换为默认球员。

当前 200 名配置球员没有发生冲突，但自定义配置和手工新秀仍可能触发。建议在配置/选秀入口按最终 ID 校验唯一性，并把不可接受的冲突直接反馈给用户。

### P3：冻结模式的配置回退包含不可达分支

`football_simulator/runtime.py:39-46` 在 `bundled_path.exists()` 时已经返回；后续再次以同一条件尝试复制到用户目录，因此复制分支永远不会执行。若设计意图是把内置配置播种到用户目录，需要重新排列判断；若无需该回退，应删除死代码并简化错误信息。

## 建议实施顺序

1. **先保护用户数据**：统一存档名/路径包含性校验，改为原子写盘并增加最近备份。
2. **修复发布阻断**：修正 Windows spec 的英文配置输入，明确 macOS 架构，统一依赖安装逻辑。
3. **建立最低测试网**：先覆盖路径、赛程、三赛季状态机、交易/选秀不变量和旧存档加载。
4. **再做结构拆分**：以行为保持为前提，把 `state.py` 分域，消除 UI/CLI 的重复排序和格式化逻辑。
5. **整理分发策略**：二进制迁移到 Releases/LFS，源码仓库保留可复现构建材料和校验和。

## 最终评价

项目最可贵的部分是“系统真的连起来了”：配置、联赛、杯赛、升降级、交易、选秀和历史能够连续运行多个赛季，玩法广度和实现投入都明显高于普通原型。当前并不需要推倒重来；更合适的方向是暂停扩张一轮，用路径安全、原子存档、自动化测试和可复现构建把现有成果托住。

完成上述 P1 项和最低测试网后，项目整体质量可从当前约 6.8/10 提升到一个更适合公开持续发布的水平。
